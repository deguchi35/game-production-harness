# Claude Codeへ渡す準備プロンプト

初めて使う場合は[QUICKSTART](../docs/QUICKSTART.md)から進める。WindowsのClaude Desktopで **Code → Local → 対象Unityプロジェクト** を選び、最初はManualなど承認を確認できるモードを使う。Chat／Coworkへ貼ることやCloudを選ぶことでは、同じローカル接続確認にならない。

このキットには実行可能なハーネスや生成スクリプトはまだない。**Aを送る → 調査と計画を確認する → Bの許可範囲を記入して送る**、の順に進める。同じScene／.blendを別セッションが編集中なら統合し、二重に動かさない。

## 入力欄

次の値をAの先頭へ付ける。角括弧は実値に置き換える。架空の例や空欄のまま実行しない。アプリのパスだけは、わからなければ「不明」と書いてよい。

```text
HARNESS_REPO：［このキットを展開した絶対パス。資料を添付する場合は「添付」］
PROJECT_ROOT：［Assets、Packages、ProjectSettingsがあるUnityルートの絶対パス］
WORK_ROOT：［実行記録用の非公開フォルダの絶対パス］
run-id：［日時と用途を含む一意の名前。例：20261015T090000Z-preflight］
Unity実行パス：［実パス／不明］
Blender実行パス：［実パス／不明］
今回の確認対象：［自作道路1個を扱う既存Scene、または調査後に提案］
追加支出上限：0円。既存のClaude契約枠だけを使用。
```

`WORK_ROOT`は原則として公開キットとゲームのリポジトリ外に置く。非公開ゲーム配下に置く場合はGitの追跡対象外と確認してから書き込む。フォルダ外へのアクセス権がない場合は、必要なフォルダだけについて確認する。アクセス拒否を回避せず、公開キットへ私的証拠を移して代用しない。

## A. 調査と計画（最初に送る）

あなたは3Dゲーム制作ハーネスの実装担当です。今回は環境調査と最小実装の計画まで行ってください。ゲームのソース、Scene、Prefab、.blend、依存パッケージはまだ変更しないでください。新規ハーネスコードの作成・実行、アセット生成、アプリ起動、ビルド、ソフトのインストールも、この段階では行いません。

入力欄のPROJECT_ROOTを実際に確認してください。README.md、docs/QUICKSTART.md、docs/WORKFLOW.md、docs/HARNESS_SPEC.md、docs/SOURCES.mdをHARNESS_REPOまたは添付から読み、読めたファイル名を答えてください。プロジェクト側の既存CLAUDE.md等も確認し、上書きしないでください。資料やプロジェクトにアクセスできなければ、読んだふりをせず不足を知らせてください。

このキットは文書と設計だけで、doctor／plan／generate等のCLI、schemas、生成・検査スクリプトは未実装です。設計上の名称を既存コマンドとして実行しないでください。

読み取り中心で、次を確認してください。

1. 現在の作業フォルダ、Unityプロジェクトの実パス、ProjectVersion.txtのEditor版、レンダーパイプライン、対象Scene候補。
2. 実在するUnity／Blender／Gitの場所と、ファイルや既存設定から確認できる版。未確認の版は不明と記録する。指定パスが不明なら、オーナーの指定や一般的な導入先など必要な範囲だけを確認し、全ドライブを走査しない。
3. 既存MCP、スキル、依存ライブラリの有無と参照元。設定内の秘密値を読んだり出力したりせず、起動・有効化しない。設定ファイルの存在だけで接続成功としない。
4. Git差分、未追跡ファイル、.blend、Unityの.meta、画像・音源を守るバックアップ、専用ブランチ、復旧方法。調査では既存変更を消さず、ブランチ切り替えやバックアップ実行も計画に留める。
5. 音入り録画の手段、Android Build Supportと対応SDK／NDK／OpenJDK、実機接続の確認方法。未実行のものは未確認とする。

不足するソフトや権限があれば、その工程をblockedにしてください。インストールコマンドや実行パスを推測せず、公式取得元URL、版、ライセンス、必要権限、互換性、導入理由を示して承認待ちにします。Unity更新、認証設定変更、全権限許可、MCPポートの外部公開、有料API・購入・新契約は行わないでください。

最小構成はMCPなしのBlender Python／CLIとUnityの既存機能を基本にしてください。必要なスクリプトは今後実装するものとして、ファイル名・保存先・役割を提案します。GUI操作が必要なら、使える操作手段を実証する計画か、オーナーが行う操作を示してください。新しいMCPやスキルを入れることを前提条件にしないでください。

最初の計画は「環境確認 → 既存状態の保護 → 自作道路1個 → 実画像レビュー → 数値検査 → Unity表示 → 証拠付き報告」に絞ってください。音入り録画、Androidビルド、停止・再開の検証を続く小さな工程に分けます。各工程の変更対象、入力、出力、合格条件、必要な許可、タイムアウト、失敗時の復旧方法を示してください。全体の停止時刻と、終了前に確保する保存用の余裕時間も計画に含めます。

この段階で書き込んでよいのは、指定されたWORK_ROOT/runs/<run-id>/のPREFLIGHT_REPORT.mdとHANDOFF.mdだけです。書き込み権限がない／Planモードで保存できない場合は、内容を会話で返し「ファイル未保存」と明記してください。HARNESS_REPOやゲームの公開用フォルダへ書き込まないでください。

計画と承認待ちを提示して停止してください。オーナーがBで対象と範囲を明示するまで実装へ進まないでください。

## B. 合意した最小実装と接続確認（計画確認後に送る）

下記の許可範囲を埋め、確認した計画と一緒に送る。空欄、曖昧な「全部許可」、未決定の依存導入は実装の承認として扱わない。

```text
採用する計画：［Aで確認した計画の見出し／版］
使用するPROJECT_ROOT／WORK_ROOT／run-id：［Aと同じ実値、または承認する変更］
復旧方法と専用ブランチ：［バックアップ先、既存変更の保護方法、ブランチ名］
実装・変更を許可する対象：［スクリプト保存先、Scene、Prefab、生成専用フォルダ等］
許可するアプリ起動・検証：［Blender生成、Unity取り込み・再生、録画、Androidビルド等の具体的範囲］
追加導入：なし。別途承認済みの場合は［ソフト・固定版・取得元・許可範囲］
停止時刻：［YYYY-MM-DD HH:MM、タイムゾーン］
各工程のタイムアウト：［Aで合意した値］
保存用の余裕時間：［停止時刻の何分前に新規作業を止めるか］
追加支出上限：0円。
```

上記で承認した計画と範囲だけを実行してください。最初にパス、現状の差分、同時編集の有無を再確認し、復旧地点を作ってから進めます。許可したパス外への書き込み、元データの削除、公開、push、mainマージは含みません。

合意した最小スクリプトを実装し、実在するアプリで実行してください。スクリプトを作成しただけ、モックが成功しただけでは、Blender／Unity実行成功とはしません。既存のEditorと同じプロジェクトをバッチ処理で同時に開かず、強制終了やロック削除で回避しないでください。

自作道路モジュール1個について、固定カメラで撮影し、画像を実際に開いて対象ファイルと指摘を残してください。寸法、原点、UV、材質、欠落テクスチャを検査します。GLBまたはFBXは実プロジェクトの対応状況から選び、書き出しとUnity取り込み、コンパイル、Play表示をそれぞれ記録してください。見る手段がなければ画像レビューはblocked／not_runにし、人による確認が必要と記します。

許可されている場合は、ゲーム内の接地・離地・着地イベントから短い音を鳴らし、実プレイの音入り録画を取得してください。録画範囲はゲームウィンドウとゲーム音だけとし、通知、別アプリ、マイク、カメラを含めません。追加の収録範囲や権限は別途確認してください。音声トラック、無音、クリッピングを確認し、実際に聞いた人または利用できる評価手段と結果を記録します。AudioSourceの設定やファイルの存在だけで音の試聴評価をpassedにしないでください。使える録画手段は実際のUnity版と実行モードで確認します。

Androidテストビルドは許可済み・必要モジュール確認済みの場合だけ実行し、コマンド、終了コード、生成物を記録します。端末がない場合は実機実行・性能測定をnot_runとします。保存後に中断し、保存データから安全に再開できるかを検証します。未承認の操作が必要になったら、その工程を止めて具体的に確認してください。

同じ合格条件に対する自動修正試行は最大2回です。各試行の内容・結果・回数を保存し、セッション再開、別run、担当変更でも未解決条件の回数や予算をリセットしないでください。2回で解決しなければ保留し、原因・復旧地点・次案を残します。別条件へ言い換えて無制限に再試行しません。

各工程のタイムアウトと全体の停止時刻を守り、保存用の余裕時間に入ったら新規作業を始めません。クラッシュ・時間切れ・未確認の終了はpassedにしないでください。利用枠や追加費用が必要になっても別サービスへ切り替えません。安全に保存し、次の報告形式で結果を更新してください。

## 報告の保存先と必須項目

基準は**WORK_ROOT**。`runs/<run-id>/`はこのフォルダの配下を意味し、HARNESS_REPOからの相対パスではない。PREFLIGHT_REPORT.mdとHANDOFF.mdを更新し、指示文そのものは上書きしない。証拠は同runのlogs/、images/、video/、builds/へ保存する。未作成の証拠をファイルとして捏造しない。

PREFLIGHT_REPORT.mdには以下を記す。これは報告書の記述形式であり、検証済みJSONスキーマや自動判定器の提供を意味しない。

- 実行識別：run-id、開始・終了日時とタイムゾーン、キットの版／コミット、ゲームのコミットと未コミット差分の有無。取得不可は不明。
- 環境：PROJECT_ROOT、WORK_ROOT、OS、各アプリの実パス・版、操作方式、追加依存。秘密値は書かない。絶対パスは非公開報告内だけ。
- 許可と保護：承認した計画、変更対象、バックアップ・復旧地点、作業担当、支出上限、停止時刻、各工程のタイムアウト、保存用余裕時間。
- 工程別結果：工程ID／名称、状態、入力・出力、実行コマンド、終了コード、今回の証拠への相対パス、観察者、観察内容、未確認理由、同一合格条件の修正試行回数、次の操作。
- 変更ファイル一覧、実測できた時間・使用量・費用、オーナーへの確認事項。

状態は`pending`、`running`、`passed`、`failed`、`blocked`、`not_run`を使う。Aの調査で実行していない項目は`not_run`、必要条件が欠けて実行できない項目は`blocked`。今回の実行ログと過去のログは別欄にする。

入力・設定・出力の識別とレビュー対象のSHA-256はdocs/HARNESS_SPEC.mdの証拠契約に従う。未コミット差分も識別し、証拠の存在だけでなく、想定形式で読めることと今回の入力・試行との一致を確認する。秘密値をコマンドやログへ残さない。

最低限、次は別々の行で記録する：環境確認、バックアップ、Blender生成、書き出し、数値検査、画像レビュー、Unityインポート、Editorコンパイル、Play表示、音声収録、音の試聴評価、Androidビルド、端末起動、端末性能測定、停止・再開。必要な証拠が存在するかを確認し、未実施・失敗・ブロックをpassedへ置き換えない。

HANDOFF.mdには、最後の検証済み地点、変更途中のファイル、次に行う操作と前提条件、再開時の確認方法、未解決条件の累計試行回数と残り予算、保留中の承認を記す。実装していない再開コマンドを案内しない。

## 夜間作業へ移る前の確認

- [ ] 対象フォルダ・書き込み担当・復旧地点を確認した。
- [ ] Blender→Unityの代表アセットと実画像レビューを確認した。
- [ ] 保存・停止・再開を検証した。
- [ ] 音声収録と試聴評価の結果を別々に記録した。
- [ ] Androidビルドの結果を記録した。音／Androidの不足がある場合は、影響と夜間に除外する範囲を示して限定作業の明示承認を得た。
- [ ] 実機未確認を合格にしていない。
- [ ] 夜間の変更対象・終了時刻・各工程のタイムアウト・保存用余裕時間・予算を決めた。
- [ ] レポートと証拠の実ファイルが保存され、オーナーが場所を確認できた。

基本の往復・復旧・停止再開を確認するまで夜間の大量生成へ進まない。この準備作業だけで夜間実行を開始せず、[OVERNIGHT.md](OVERNIGHT.md)で確認済みの範囲を改めて指定する。


準備終了時は、確認できた実パス・版・許可済み範囲を使って、OVERNIGHT.mdの入力欄を埋めた次回用指示案も提示してください。停止時刻、予算、未確認事項への承認は推測せず、オーナーが決める欄として残してください。オーナーに同じ情報を再入力させないでください。
