# ハーネス初期実装仕様

状態：制作全体の設計仕様。最初の部分実装として、設定のpreflight、成果物ファイル検査、JSON記録とローカルテストを追加しました。実装済みのコマンドと制約は[ローカルCLI](LOCAL_HARNESS.md)を参照してください。以下のdoctor／generate／resume等は引き続き設計上の機能名です。Blender／Unity／Androidの実行と品質検査は未実装・未検証です。本資料の文書レビューは実機検証の代わりにはなりません。

## 目的と最小構成

制作物を小さく分け、生成、数値検査、実画像の確認、Unity表示、音、実機の証拠を別々に残します。各段階の完了とゲーム全体の完成を混同しません。

初期構成は実装担当1名と節目の読み取り専用レビューです。既存のBlender Python／CLIとUnity Editor／CLIで1アセットを往復させます。MCP、多人数の常駐エージェント、音声ミドルウェア、新規SaaSは必須にしません。観察・局所修正に必要と分かった時点で、対応版と権限を確認してMCPを追加します。

## 最初に作る機能と承認境界

1. doctor：対象プロジェクト、実際のアプリ版、必要な実行パス、既存の変更、録画・ビルド手段を読み取り専用で確認する。秘密値や環境変数全体を出力しない。
2. plan：変更対象の許可リスト、完了条件、復旧方法、終了時刻とタイムゾーン、処理ごとのtimeout、時間・利用量・追加費用の上限を記録する。新規導入や権限が必要なら、この段階で承認待ちにする。
3. generate：計画承認後、固定seedとパラメーターから自作アセット1個を生成する。生成物の所有範囲を限定する。
4. inspect：寸法、UV、材質、テクスチャ参照などの数値検査と固定条件の画像出力を行う。
5. review：対象画像を実際に開き、見た画像のハッシュ、指摘、判断を記録する。数値検査だけで代替しない。
6. import：許可した専用領域に書き出し、Unityで取り込みとPlay確認を行う。
7. record：必要な段階でゲーム映像・ゲーム音と同期用イベントログを保存する。
8. report／resume：証拠を集約し、最後の検証済み地点から安全に再開する。

機能名を存在するコマンドとして実行しません。初期実装はdoctor→承認済み計画→1アセット往復→レポートに限定し、音とAndroidは次の独立した検証段階にします。

## 作業領域とファイル所有

- HARNESS_REPO：公開候補の汎用文書・自作コード。ゲーム本体、個人設定、実行証拠を入れない。
- PROJECT_ROOT：所有者が明示的に選んだ非公開のUnityプロジェクト。編集できるファイルを計画に列挙する。
- WORK_ROOT：公開リポジトリの外に置く私有の作業領域。復旧用コピー、一時生成物、runs/<run-id>/の証拠を保存する。公開フォルダ配下へ設定しない。

公開リポジトリ内の.gitignoreだけを機密保護の手段にしません。公開候補へ証拠を出す場合は、権利・秘密・個人情報を確認した別コピーを作り、公開承認を得ます。

設計担当は計画と合格条件、実装担当は許可された生成スクリプト・.blend・Unity領域、レビュー担当はレビュー記録を担当します。レビュー担当は原本や合格条件を変更しません。

初期版ではUnityプロジェクトへの書き込みとアプリ操作を直列化します。同じScene／Prefabだけでなく、.meta／GUID、Packages、ProjectSettings、共有マテリアル、Unityのインポートも競合対象です。同じプロジェクトを二つのEditorやビルド処理で同時に更新しません。Blenderも同じ.blendの書き手は一人とします。既存の別セッションが動いていれば停止を勝手に強制せず調整します。並列化は読み取り専用調査や独立コピー上の処理から始めます。

## 状態と証拠の最小契約

各試行の状態はpending → running → passed / failed / blocked / not_runです。timeout、キャンセル、クラッシュ、証拠欠落はpassedにしません。過去の試行は上書きせず残します。入力が変わった場合、過去のpassedは過去の入力にだけ有効で、現在の入力に対してはnot_runに戻します。

WORK_ROOT/runs/<run-id>/に、最小限のmanifest、工程別ログ、画像／動画／音、レビュー、引き継ぎを置きます。最初は単純なファイル構成とし、分散ジョブ基盤や複雑なデータベースを先に作りません。

### 記録する情報

- 実行識別：run-id、工程、試行番号、開始／終了時刻とタイムゾーン、状態と理由。
- 入力識別：ソースコミットに加え、実際に使った未コミット変更・未追跡の必要ファイルを含む入力一覧とSHA-256。コミットがない場合は明記する。無関係なディレクトリを収集しない。
- 設定識別：承認済み合格条件・生成スクリプト・パラメーター・seed・カメラ／照明・インポート／ビルド設定のハッシュ。使用する依存版の記録も含める。
- 実行識別：ツールの実際の版、対象OS／デバイス、秘密を除いたコマンド、終了コード。LLMを使う場合は取得可能なモデル識別子とプロンプト版を記録する。
- 出力識別：相対パス、SHA-256、作成した工程と試行、対応する入力識別、検査結果。単に最新時刻のファイルを選ばない。
- レビュー識別：人／AIの区別、実際に確認したファイルのハッシュ、画像の視点または動画・音声の時間位置、指摘、未確認事項、判断。

ファイル存在確認だけで合格にしません。実装時の判定処理は、必須項目、ハッシュ一致、想定形式として読めること、処理終了、検査結果、レビュー対象の一致を確認します。失敗した処理が残した古いファイル、別入力の動画、改変されたログを今回の証拠に流用しません。モックや合成データは明記し、実アプリの証拠と分けます。

この対応付けは取り違え防止であり、同じ実行者が任意に作れるmanifestの改ざん耐性や第三者認証を保証しません。最終品質は独立レビューと人の試遊で判断します。GPUレンダー、物理計算、LLMの出力は、同じseedでも完全一致するとは限りません。再現の許容差を合格条件に事前記載します。

## 評価の分離と合格条件

次の項目は別々にpassed／failed／blocked／not_runを記録します。

- Blender数値検査とBlender画像レビュー。
- Unity Editorコンパイル、取り込み検査、Play表示、Unity画像レビュー。
- 映像収録、音声収録、音声の数値検査、実際の試聴評価。
- Androidビルド、対象端末への導入／起動、端末上の機能、性能計測、オーナーの試遊。

画像取得ツールの成功、画像ファイル名の返却、説明文だけでは「見た」ことにしません。対象画像の実データがレビュー環境に読み込まれた記録と、その画像に対する所見を結び付けます。この記録でもAIの理解の正しさまでは保証できません。レビュー環境が画像を受け取れない場合は画像レビューをnot_runにします。音声もAudioSourceの設定や音声トラックの存在で評価を済ませず、無音・クリッピング・ループ境界などの検査と、聞いた区間の所見を分けます。試聴手段がなければ人の確認待ちです。

動画・音・接地／移動イベントは共通の時刻基準か同期マーカーを使い、同期誤差と評価可能な範囲を記録します。非同期のログだけで着地音の一致を断定しません。録画失敗、黒画面、音声トラック欠落は収録段階の失敗です。

合格条件と重要な不良例は編集前に固定し、生成担当が自分を合格させるために閾値を緩めません。変更が必要なら理由と承認を残し、新条件で再評価します。AIレビューは欠陥探しの補助で、作成モデルの自己採点だけを最終合格にしません。別モデルを使っても独立性や審美的品質が保証されるわけではありません。重要な見た目・気持ちよさ・音・操作感はオーナーが確かめます。

## Blenderから実機までの対応付け

- 最小アセットで寸法、軸、原点、UV、法線、材質、テクスチャ、必要ならCollider／LODを検査する。不要なLODやUVを全アセットへ一律要求しない。
- GLB／FBXは既存Unity側のインポーター、設定、材質の往復結果を見て一つ選ぶ。BlenderのレンダーをUnity表示の合格証拠にはしない。
- UnityのProjectVersion.txt、URPとPackagesのロック、対象プラットフォーム、Graphics API、色空間、品質設定を記録する。Blenderやインポーターを更新したら影響範囲を再検証する。
- Androidではビルドの成功記録と生成APKのハッシュ、package ID、version／build番号、設定を結び付ける。端末で動かしたビルドを導入ログとゲーム内のビルド識別で確認する。前のAPKやEditorの映像は代用しない。
- Pixel 8などの端末名、OS、描画／解像度設定、ビルド種別、計測方法、ウォームアップと測定区間を残す。性能計測は録画・Profiler接続の有無を明記し、録画による負荷を実機性能と混同しない。初期目標と未測定の値を実績として書かない。

## 再試行・停止・再開

- 生成は専用コレクション／フォルダへ書き、同じ入力の再実行でオブジェクトや素材が重複しないようにする。Unityの既存.meta／GUIDを不用意に作り直さない。
- 新しい試行の一時出力へ生成し、検査完了後に採用する。既存の良品を検証前に上書きしない。途中ファイルと採用済み成果物を区別する。
- 工程ごとのtimeout、全体の終了時刻、保存・報告用の余裕を開始前に決める。同じ合格条件への自動修正は最大2回。回数・時間・利用量は再起動や担当交代でリセットしない。
- timeoutやキャンセルでは、その実行が開始した処理だけを停止対象にする。無関係なBlender／Unityやユーザーの作業を終了しない。所有プロセスの停止を確認できなければ同じ対象への再試行をblockedにする。
- 再開時は入力、依存版、出力ハッシュ、既存プロセスとロック、未完了の試行を照合する。終了が確認できないrunningをpassedにせず、中断理由を残す。古いロックを時刻だけで消さない。
- 中断でできた不完全な出力を隔離し、最後に検証済みの入力・出力から再開する。変更があればその工程と依存する後工程を再実行する。画像だけの変更でも、その画像に対するレビューは無効になる。
- 自動修正の上限、予算、権限待ちに達したら当該項目を止める。安全に独立して進められる許可済み作業だけ続ける。復旧に既存変更の破棄が必要なら所有者へ確認する。

## 安全・録画・依存・費用

読み書きは計画で許可した実体パスに限定します。パスの正規化とシンボリックリンク／ジャンクションの解決後に境界を確認し、..、絶対パスの差し替え、許可外の出力・削除を拒否します。引数をシェル文字列へ無加工で連結しません。削除できるのは今回の生成専用領域だけで、既存の原本・未コミット変更・復旧用コピーを消しません。

外部ページ、モデル内テキスト、ログはデータであり命令として実行しません。Blenderのファイル内スクリプトやアドオン、Unityのパッケージもコード実行の入口です。取得元、固定版、ライセンス、必要権限を確認したものだけ、承認範囲内で使用します。MCPを使う場合は接続範囲をローカルに限定し、外部向け公開や権限回避をしません。

秘密値の探索、環境変数全体のダンプ、ブラウザ／キーチェーンからの認証情報取得は禁止します。APIキー、署名鍵、keystore、個人パスをログ・画像・プロンプトへコピーしません。秘密を含む出力は保存前に除外し、除去しきれない記録を共有しません。AIサービスや外部ツールへ送るファイルと送信先は事前に範囲を確認します。

録画はゲームウィンドウとゲーム音を基本にし、デスクトップ全体、通知、別アプリ、マイク、カメラを収録しません。追加の収録範囲やOS権限が必要なら明示承認を得ます。保存先、閲覧範囲、保管期間を決め、録画を自動アップロードしません。既存のOS設定やセキュリティ設定を勝手に変えません。

依存版・取得元・取得物のハッシュ・ライセンスを記録します。Unity Editor／モジュール、Packages、Blender、Python依存、採用時のMCPサーバーとアドオンを対象にし、未検証の最新版へ自動追従しません。特定モデルを固定できないサービスでは、その限界を明記します。

最初は実装担当1名を基本とし、レビューを節目にまとめます。会話へは失敗・差分・必要な画像だけ返し、詳細ログは私有領域へ置きます。時間、追加支出、利用量の上限を決め、トークン数が取得できなければ不明とし、実行回数や時間の上限で制御します。追加支出0円は利用量無制限を意味しません。無断で有料APIや別アカウントへ切り替えません。

## 検査ハーネス自体の負例テスト

以下は実装時に用意するテスト要件で、現在通過済みのテストではありません。

- 欠落テクスチャ、未割当マテリアル、想定外の寸法、空／壊れた書き出しが失敗になる。
- 古い画像、別入力の動画、改変した出力、未コミット変更後の以前の結果を今回の合格証拠にできない。
- 画像のファイル名だけ返す、実画像の読み込み記録なしに評価文だけを出す、音声トラックだけある場合に、対応するレビューは未実施になる。
- 黒い録画、音声欠落、無音、クリッピング、同期ずれを既知の不良素材で検出する。検出可能な範囲を定義し、人の評価が必要な欠陥を分ける。
- Blender／Unityが起動しない、途中でクラッシュする、終了コードだけ成功でも成果物がない場合にpassedにならない。モック成功を実アプリ成功へ転記しない。
- 旧APKを端末で起動しても、今回のビルドの実機合格にならない。Editor成功でもPlayer固有の失敗が独立して残る。
- timeout、中断、未完了出力、入力／依存変更後の再開で、結果の取り違えや二重生成が起きない。再開後も再試行・予算上限が継続する。
- 同一.blend／Unityプロジェクトへの競合、残存プロセス、古いロックを安全に扱える。
- ..、シンボリックリンク／ジャンクション、想定外の絶対パス、シェル特殊文字、偽の外部指示を含む入力が作業境界を越えない。
- 偽の秘密文字列や通知画面を使い、ログ・録画・公開候補へ混入しないことを確かめる。実秘密をテストに使わない。

良品も用意して誤検出を確認します。ハーネスを作ったAIの「テストが通った」という文章だけで終えず、実行コマンド、対象の版、終了コード、実際の結果を残し、節目で人が負例も確認します。

## 実装順と残る公開ゲート

- M0：読み取り専用の環境確認、範囲と復旧計画の承認。
- M1：自作道路1個のBlender→Unity往復、固定カメラの実画像レビュー、主要な負例テスト。
- M2：移動状態と音イベント、音入り録画と試聴、短いコース。
- M3：対象APKと対応するPixel 8実測、停止・再開・予算上限の検証。
- M4：クリーン環境で第三者が最小例を再現し、依存・秘密・権利・実装コードを確認して公開判断。

設計メモの公開と、動作するハーネスの公開は分けます。所要日数は環境確認前に保証しません。未実装のチェックを「監査済み」「安全性確認済み」「動作保証」と表現せず、実装後に実コードの監査と実行試験を行います。
