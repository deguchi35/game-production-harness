# 3Dゲーム制作の手順書

更新日：2026-10-15。これは今後の制作・検証手順です。実行可能なハーネスは未実装で、記載したテストが既に成功したという報告ではありません。文書レビューで手順の不足は直せますが、コード監査とBlender／Unity／Androidの動作試験は実装後に別途必要です。

初めて準備する場合は[セットアップ手順](QUICKSTART.md)を参照してください。ここでは、代表アセット1個の往復を確認した後に目指す制作全体の手順も示します。

## 1 まず決める完成範囲

最初は30〜60秒遊べる1区間に絞ります。直線加速、緩いカーブ、トラックを避ける区間、ジャンプ台、着地、終了／再挑戦を含めます。都市全体や大量の建物を先に作りません。名古屋駅から栄へ向かう構想は維持できますが、初回検証では街の再現範囲を短く限定します。実在の街を正確に再現したと宣伝するには別途、地理データの出典と精度検証が必要です。

### 最初の合格条件

| 対象 | 確認方法 | 初回の判断基準 |
|---|---|---|
| 見た目 | 同じカメラの比較画像 | 主役と道路、建物に意図した素材。ピンク／欠落マテリアルなし。主要な貫通なし |
| 速度感 | 同じ区間の実プレイ動画 | 低速と高速を見分けられる。近景の流れ、加速時の画角変化、旋回の反応が協調する |
| 音 | 音入り録画とイベント時刻ログ | 滑走・旋回・離地・着地を区別できる。着地の二重発音や空中での地面摩擦音がない |
| ゲーム性 | 手動プレイ | 避ける、曲がる、跳ぶに選択があり、失敗後に再挑戦できる |
| UI | 日本語で一周操作 | 開始、停止、再挑戦、終了が使える。英語切替は設定から |
| Android | Pixel 8で実機計測 | 暫定目標60fps。15分走行時のフレーム時間、発熱傾向、メモリを記録して判断 |

60fpsは既存実装の保証値ではなく目標です。P95フレーム時間16.7ms以下を目安に置き、達成不能なら結果と変更理由を残して画質設定や目標を見直します。合格させるためだけに基準を書き換えません。測定するAPK、端末OS、解像度／品質、ビルド種別、ウォームアップ、測定区間、計測方法を固定し、平均fpsだけで判定しません。録画・Profiler接続の負荷がある測定は明記します。Editorで速いだけでは合格にしません。画像や音の評価が未実施なら、その項目は「未確認」です。

## 2 誰がどこで作業するか

- オーナー：参考映像と画風の確定、必要なインストール・権限・費用の承認、Pixel 8での試遊、最終品質判定。
- 設計担当：仕様と合格条件、参考資料、タスクの分割、成果物のレビュー、未確認事項の管理。
- 許可したローカル環境のClaude Code：実装とBlender／Unity操作。実際の起動方式と接続状態を確認する。ブラウザ版を選ぶ場合はローカルBlenderとUnityにアクセスできる仕組みを別途実証する。特定端末が現在オンラインという前提ではない。
- 実装担当：最初は1担当。同じUnityプロジェクトと.blendへの書き込み・アプリ操作は直列にする。.meta、共有材質、Packages、ProjectSettingsも競合対象。別Editorやビルド処理との二重操作を避ける。レビュー担当は原則読み取り専用。
- 並列化：仕様調査、音素材のライセンス確認、独立したテスト作成など、共有シーンを変更しない作業だけ。

役割を分けることと、別のAIを常時起動することは別です。実装担当1名＋節目のレビューから始めます。モデル名と画像・音を実際に確認できる機能を確認して記録し、最初はモデルを増やさず実行時間と修正率を測ります。別モデルを使っても品質保証にはならず、最終的な見た目・音・操作感はオーナーが確認します。

## 3 必要な環境を確認する

1. Unity HubとプロジェクトのProjectVersion.txtで実際のEditor版を確認する。手元で共有されていた版だけを現在の導入証拠にせず、最新への一括更新はしない。
2. Android Build Supportと、そのEditorに対応するSDK・NDK・OpenJDKを確認する。
3. Blenderの実際のバージョン、Python／CLIの利用可否、空き容量、GPUドライバーを確認する。UnityのURP／Packagesロック、インポーター、必要なCLI依存も固定版を記録する。
4. Git、Claude Codeのログイン状態と利用枠を確認する。認証情報そのものを読み出さず、環境変数全体を出力しない。APIキーや署名鍵をチャット・ログ・公開リポジトリへ貼らない。
5. 初回はMCPなしのBlender Python／CLI＋Unity Editor／CLIを基本にする。必要と分かってからBlender MCPの公式版とコミュニティ版を比較し、同時導入を前提にしない。
6. CoplayのBlender Bridgeを使うなら、その対応アドオン・ポート・バージョンを先に確認する。公式版と互換だと推測しない。
7. 新規SaaSは初回不要。既存契約内で始め、有料APIや有料素材は個別承認後。
8. 画面録画・アプリ操作などの許可は必要なものだけ。ゲーム音の収録にマイクを使う前提にせず、権限全許可やBypassモードを前提にしない。

この段階は読み取り専用です。アプリ起動・取り込みでファイルを変更する試験、インストール、設定変更は、変更範囲と復旧計画を承認してから行います。

MCP経由のPythonも任意コード実行です。Blenderファイル内のスクリプトやUnityの外部パッケージも確認対象です。プロジェクト専用フォルダ／必要なら隔離環境で動かし、外部公開ポートや秘密情報を含む作業領域へのアクセスを避けます。インストール先、取得元、固定版、ライセンス、権限を確認してから有効化し、外部資料の文章を実行指示にしません。

## 4 昼間に通す接続確認

### A 読み取り専用の確認と計画

対象プロジェクト、既存Git差分、未追跡ファイル、同じ対象を使うセッションを確認します。許可するファイル、復旧方法、新規導入の有無、終了時刻とタイムゾーン、処理ごとのtimeout、追加支出・利用量の上限を提示し、承認を待ちます。公開／pushは含みません。

公開用のHARNESS_REPO、非公開ゲームのPROJECT_ROOT、公開リポジトリ外にある私有のWORK_ROOTを分けます。WORK_ROOT/runs/<run-id>/を記録先にし、公開フォルダへゲームや実行ログをコピーしません。.gitignoreだけで機密を守れるとは考えません。

### B 承認された最小アセットの往復

1. 既存差分、未追跡データ、.blend、Unityの.meta、音源・画像を含む復旧地点を作り、戻せる範囲を確認する。ブランチだけでは未コミット変更や大きなバイナリのバックアップにならない。
2. 専用ブランチと生成用フォルダで作業する。元の変更を消さず、同じUnityプロジェクト／.blendの書き込みは一担当にする。
3. 自作の道路モジュール1個をBlenderで生成し、名前・寸法・原点・材質・パラメーターを記録する。
4. 固定カメラと照明で撮影し、実際の画像を開いて指摘と判断を残す。画像を受け取れない場合は未実施とする。
5. GLBまたはFBXから、既存Unity側インポーターと材質再現を確認できる形式を一つ選ぶ。
6. Unityへ取り込み、メートル単位、軸、法線、UV、テクスチャ、原点、必要なCollider／LODを点検する。Blender画像とUnity表示は別に確認する。
7. Editorのコンパイル、Play表示を別項目で記録する。欠落テクスチャなどの自作不良例も検査し、常に成功を返すだけの検査になっていないことを確かめる。
8. 同じ入力で再実行して重複生成しないこと、途中停止後に安全に再開できることを確認する。

### C 次の段階の接続確認

Bの結果を見てから、滑走音／着地音と音入り録画、Androidテストビルドへ進みます。音声収録と試聴、Androidビルドと端末の起動・実測はそれぞれ別です。端末がなければ「ビルドのみ／実機未確認」とします。

初回から音・実機まで全て自動で成功すると約束しません。未確認の段階を夜間作業の前提にせず、制約と影響を示し、オーナーが認めた限定作業だけ進めます。基本の往復、停止・再開、復旧を確認できるまでは夜間の大量生成へ進みません。

## 5 制作ループ

### 5.1 参考と設計

参考映像の時間位置ごとにカメラ高さ、追従遅延、速度変化、画角、近景の密度、障害物の予告、ジャンプ時間、着地、音を表にします。映像を見られなければ詳細解析済みとは記しません。映像の内容・キャラクター・音素材をそのまま複製せず、体験を構成する要素を独自実装します。

代表画像3枚程度と、避けたい表現を用意します。各画像の利用許諾も記録します。最初に建物1棟、道路1区間、トラック1台の見た目を決め、合格したルールをモジュールへ展開します。

### 5.2 Blender生成

繰り返す処理はPython／CLIへまとめ、入力パラメーターとseedを保存します。MCPを採用した場合は現状の観察と局所修正に使います。長い会話の中だけに形状ルールを置きません。生成専用領域に試行ごとの出力を作り、検査前に既存の良品を上書きしません。再実行でオブジェクトや素材が増殖しないことも確認します。

ポリゴン数を増やすだけでなく、シルエット、面取り、適切な法線、UV、PBR素材、光、接地感を整えます。近くを高速で通過する道路端・柵・路面模様を優先し、遠景は負荷を抑えます。詳細モデルからノーマル等へベイクする工程は、必要性を確認して追加します。

### 5.3 画像と数値で点検

生成→保存→撮影→画像を開く→指摘記録→数値確認→局所修正→再撮影の順に実施します。

入力・設定・出力にハッシュを付け、今回実際に使った未コミット変更も入力に含めます。レビューは見た画像のハッシュと視点を記録します。画像を書き換えたら以前のレビューは引き継ぎません。ファイルの存在や同じコミット名だけでは合格証拠になりません。詳細は[実装仕様](HARNESS_SPEC.md)の証拠契約を使います。

数値検査の例：欠落テクスチャ数、未割当マテリアル数、極端な寸法、三角形数、LOD有無、UV有無、境界箱、原点。個別アセットの三角形数やテクスチャ予算は、Pixel 8の実測を踏まえて設定します。根拠なく全モデルへ同じ上限を適用しません。

### 5.4 Unityで成立させる

実プロジェクトのURP版、Graphics API、色空間、品質設定を記録してマテリアルを検査します。Editorコンパイルが通ってもAndroid Playerのシェーダー・入力・音・権限が通るとは限りません。端末では、今回のAPKハッシュと導入ログ・ビルド識別を結び付け、以前のビルドを誤って評価しません。

カメラは低さだけに依存させません。速度に合わせた画角・遅れ、近景の流れ、適切なコース幅、旋回時の傾き、着地時の小さな反応を組み合わせます。画面揺れは設定で弱められるようにします。

ゲーム進行はPhysics／入力／カメラ／音／VFXの責務を分けます。ただし過大な抽象化やフレームワーク刷新を先にせず、既存Controllerを再利用できるかを調べます。

### 5.5 音を物理状態から鳴らす

共有状態として速度、接地、接地面、横滑り量、加速度、離地、衝突・着地イベントを渡します。キー入力の有無だけで音量を決めません。

- 接地滑走：路面と速度に応じたループ。停止時に滑走音が残らない。
- 横滑り：旋回・横速度に応じて擦れ音を重ねる。
- 空中：地面摩擦を止め、必要なら風音へ移行する。
- 着地：接地への遷移と衝撃量で一度だけ発音。接地判定の細かな揺れで連発させない。
- ASMR設定：BGMを弱める／切る。擦れ・風・着地の質感を残す。極端な高音やクリッピングを抑える。

最初はUnity AudioMixerで実装します。FMOD等は後で必要性と費用を判断します。適切な長さのループ素材、クロスフェード、事前ロードを検討し、録画した音を聞いて決めます。素材の商用・再配布条件は別々に確認します。

映像・ゲーム音・イベントログに共通時刻または同期マーカーを残します。音声トラックの存在、無音／クリッピングの検査、実際に聞いた区間の所見は別記録です。試聴できなければ音評価は未実施にします。録画はゲームウィンドウとゲーム音に限定し、通知、他アプリ、マイク、カメラを含めません。必要なら追加範囲と権限を先に承認し、私有のWORK_ROOTに保存して自動アップロードしません。

## 6 夜間運転

- AC電源、冷却、空き容量、ネットワーク、スリープ設定、Claudeと対象アプリの起動状態を確認。OS設定は勝手に変更しない。
- 開始／終了時刻とタイムゾーン、工程ごとのtimeout、作業範囲、時間・利用量・追加支出の上限、保存／報告用の余裕を設定。初回の追加支出上限は0円。
- 1回の生成単位を小さくし、各合格地点で保存する。
- 同じ合格条件への自動修正は最大2回。改善しなければ原因と復旧案を記録して保留。回数と予算は再起動・担当交代でリセットせず、独立した許可済み作業だけ続ける。
- timeoutやキャンセルでは自分が起動した処理だけを安全に止め、停止を確認できない対象へ重ねて再試行しない。中断中の結果を完了にしない。
- 再開前に実際の入力・設定・出力・残存プロセスを確認し、入力が変わった工程とその後工程を再検証する。未検証の途中ファイルは採用しない。
- 使用量制限や権限待ちで停止したら、その理由を報告。別アカウントや有料APIへ勝手に切り替えない。
- 就寝前に承認できなかった操作は実施しない。無人で朝まで動くことは保証しない。

## 7 朝のレビュー

次の順で確認します。

1. WORK_ROOT/runs/<run-id>/MORNING_REPORT.md：完了／失敗／ブロック／未実施、今回の日時・コミット・未コミット入力の識別。
2. 30〜60秒の音入り動画：加速、旋回、ジャンプ、着地が見える。
3. 同一条件のBefore／After画像：夜間の代表区間なら最低5視点または重要局面。M1の道路1個では合意した少数の固定視点を使う。
4. 作成できたAPKなどの試遊版：ハッシュとビルド識別を示し、ビルドだけか同じ版の実機確認済みかを区別。未作成の配布物をあるように書かない。
5. 実行したテストのコマンドとログ。過去のテスト記録は別欄。
6. 追加費用、使用量、作業時間、未解決の問題。

取れなかった動画・画像・音・ビルドは、その理由と次の確認手段を明記します。AIの肯定的な文章だけで完成扱いにしません。

オーナーは「速度感」「操作の気持ちよさ」「見た目」「音」を個別に評価します。1つでも重大な不足があれば、次の区間を増やす前に代表区間を修正します。

## 8 費用と効率の測り方

既存のClaude契約、Unity Personal、Blenderを基本とし、追加契約は初回0円を目標にします。電気代、既存月額、オーナーの時間はゼロとは扱いません。定額契約でも利用量上限はあります。

各作業に開始・終了、入力／出力トークン（取得できる場合）、課金額、修正回数、合格アセット数を記録します。取得できないトークンは不明と表示し、数字を作りません。その場合は実行回数と時間にも上限を置き、無制限の再試行を避けます。長いログを何度も会話へ投入せず、失敗・差分・必要な画像に絞ります。比較指標は「1回の生成単価」より「Unityで合格したアセット1個あたりの時間・費用」です。

高機能なハーネスを増やすほど安くなるとは限りません。小さな構成で同じ課題を解き、追加の評価担当が品質改善に見合うかを比較します。
